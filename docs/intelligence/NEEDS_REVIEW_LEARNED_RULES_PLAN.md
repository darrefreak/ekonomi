# Needs Review + Learned Rules — Plan (Classification Completion Slice 1)

## Current gap

The clustering run (`TransactionClusteringService.analyse`) assigns signatures,
builds `merchant_clusters`, and resolves merchants deterministically. After that
run the state on the reference household is approximately:

- 412 transactions, 11 clusters, 195 meaningfully classified (47.3 %)
- ~6 clusters remain `classification_source = UNKNOWN`, representing ~217
  unknown transactions

Those unresolved clusters are visible through `GET /intelligence/clusters/unresolved`
but nothing lets a person answer them, and nothing remembers the answer:

1. **No cluster-level review.** The existing `/review` queue lists *individual*
   transactions with a missing merchant/category — exactly the
   one-row-per-transaction explosion this slice must avoid. The unresolved
   clusters never reach the user.
2. **No learned rules.** A correction on one transaction teaches the system
   nothing. Re-importing or re-running analysis reproduces the same unknowns.
3. **No apply-to-similar / remember-for-future actions.**

## Design

### Review is derived state, not a copied queue

An unresolved cluster *is* the review item. The queue is
`merchant_clusters where classification_source = 'UNKNOWN' and dismissed_at is null`.
This inherits idempotency from the cluster identity
(`household, signature, signature_version`): a re-run updates the cluster, so it
cannot duplicate a review item. Status:

- **OPEN** — `classification_source = UNKNOWN`, not dismissed
- **RESOLVED** — user answered (`resolved_at` set, source `USER_VERIFIED`)
- **DISMISSED** — user skipped (`dismissed_at` set); stays out of the queue

Review types, computed from the cluster's evidence:

- `UNKNOWN_MERCHANT` — no candidate at all (typically opaque references)
- `UNKNOWN_CATEGORY` — merchant known/candidate confident, category unresolved
- `LOW_CLASSIFICATION_CONFIDENCE` — candidate exists but below auto-accept

### Learned rules (`classification_rules`)

One row per `(household, rule_type, match_value)`:

- `EXACT_SIGNATURE` — match value is the signature key; carries merchant and/or
  category. Created by "Kom ihåg detta för framtiden". `user_verified = true`.
- `MERCHANT` — match value is a merchant id; carries a category for
  merchant-resolved clusters that lack one.

No free regex. Match values are produced by the existing signature normaliser,
never typed by the user or generated by AI.

### Rule precedence in `analyse()`

1. `USER_VERIFIED` transaction/cluster state — never overwritten (existing guard)
2. User-verified `EXACT_SIGNATURE` learned rule (USER_VERIFIED_EXACT)
3. Existing household merchant alias match (USER_VERIFIED_MERCHANT)
4. System merchant rule catalogue (SYSTEM_RULE)
5. Non-user-verified learned rules (LEARNED_HOUSEHOLD_RULE, future auto-learning)
6. (future AI slot)
7. UNKNOWN

When a learned rule resolves a cluster on a re-run or for newly imported
transactions, `classification_source = LEARNED_RULE` — not `USER_VERIFIED`,
which is reserved for the rows the user explicitly corrected. Coverage metrics
stay truthful: `DEFAULTED` and `UNKNOWN` never count as meaningfully classified.

### Resolution flow

`POST /intelligence/clusters/:id/resolve` with
`{ householdId, action: accept|correct|skip, merchantId?/merchantName?, categoryId?, rememberRule }`:

- validates household membership + write access; cluster must belong to household
- `skip` → `dismissed_at = now`
- `accept`/`correct` → resolve merchant (existing or created via canonical-name
  reuse), update the cluster (`USER_VERIFIED`, `resolved_at`), update the
  cluster's transactions (merchant/category, `USER_VERIFIED`) — *category and
  merchant only*: no `financial_events` or `ledger_postings` writes, so the
  ledger and net worth are untouched
- `rememberRule` → upsert an `EXACT_SIGNATURE` rule
- audit log records the decision (counts, ids — no raw descriptions)

Apply-to-similar is the same write, and the UI shows the affected count
(`transactionCount`) before applying.

### Rule management

`GET /intelligence/rules`, `PATCH /intelligence/rules/:id` (enable/disable),
`DELETE /intelligence/rules/:id` — surfaced as a minimal list under Settings.
